## Medium

### 1. Vercel Analytics 404s unless the app is actually on Vercel

`components/shell/HomePage.tsx` used to turn Vercel Web Analytics on whenever `VERCEL_ENV === "production"`. The Lighthouse job sets that variable so `robots.txt` matches production (`/.github/workflows/ci.yml`). `@vercel/analytics` then requests `/_vercel/insights/script.js`. That file exists on Vercel and does not exist in `next start`, so every lab run logged:

- `404` for `/_vercel/insights/script.js`
- `Refused to execute script … MIME type ('text/plain')`

That is the only Best Practices failure (`errors-in-console`). Accessibility and SEO are already 1.

**Impact.** The live site on Vercel is fine. The lab score, and any production-mode build that is not on Vercel, is not. Best Practices stays at 0.96 instead of 1.

**Fix.** `vercelAnalyticsEnabled()` in `lib/analytics.ts` requires both `VERCEL === "1"` and `VERCEL_ENV === "production"`. Vercel sets `VERCEL` on its own platform ([Vercel system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables)). The privacy copy is unchanged: cookieless Vercel Analytics is still on in production and still outside the cookie choice (`docs/plan.md` decision D5).

**Effort.** One predicate and a unit test.

### 2. Safari starts the canvas and the motion engine too early

WebKit in this Playwright build reports `requestIdleCallback` as missing. `components/islands/LazyHorizon.tsx` and `components/motion/MotionRoot.tsx` then used `setTimeout(..., 1600)`, while Chromium waits for idle with a 4 second cap. The comment on the horizon already says a short timeout was starting the canvas inside Lighthouse’s blocking window. That shorter path is exactly what iOS Safari and desktop Safari take.

**Impact.** On Safari the horizon canvas and GSAP/ScrollTrigger can start while the visitor is still in the first seconds of the page. That is main-thread work (the Chromium trace shows a 209 ms task on the document and further tasks in the framework chunk). It does not change the final picture. [MDN `requestIdleCallback`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback) documents the API and its limited support. [web.dev, optimize long tasks](https://web.dev/articles/optimize-long-tasks) is the reason to keep that work out of the first interaction window.

**Fix.** The fallback timeout is 4000 ms, the same cap Chromium already uses.

**Effort.** Two call sites and a source test.

### 3. Firefox does not read the prefixed text-size-adjust

`app/globals.css` set only `-webkit-text-size-adjust: 100%`. The built stylesheet had the prefix twice (Tailwind’s preflight and this rule) and not the unprefixed property. Firefox implements `text-size-adjust`, not the WebKit prefix ([MDN `text-size-adjust`](https://developer.mozilla.org/en-US/docs/Web/CSS/text-size-adjust)). Without it, mobile Firefox can enlarge text on its own and reflow the page.

**Impact.** Desktop Firefox in this run did not overflow. The risk is mobile Firefox, which is not in the Lighthouse matrix.

**Fix.** The rule now sets both properties. Chromium already honored the prefix, so the visual tests (Chromium, reduced motion) should not move.

**Effort.** One declaration.

### 4. Extra experience bullets do not open without JavaScript

`components/islands/ExperienceList.tsx` renders the extra bullets inside a div that is `inert` and `data-open="false"`. `startExperience` in `components/islands/deferred.ts` is what removes `inert`. With JavaScript off, the plus control does nothing. The first bullet and the summary stay visible. Project notes already use a native `<details>`, which works without a script.

**Impact.** A visitor or a crawler without JavaScript never sees the rest of a role. The page is still readable.

**Proposed fix, not applied.** The same native disclosure the project cards use would work without a script. It would replace the current plus button, so it changes the control. Left for approval.

**Effort.** One section’s markup and the tests that click `.exp-toggle`.

### 5. Chinese names inside English and Korean are not marked as Chinese

On `/en` and `/ko`, company names such as 坤侑科技, 巧禾數位 and 佳因企業 stay in Chinese (`lib/i18n/dictionaries/en.ts`, `ko.ts`). The header wordmark’s 鄭宏璋 (`components/islands/SiteHeader.tsx`) has no `lang`. The vertical name in the hero already has `lang="zh-Hant-TW"` (`components/sections/Hero.tsx`). A `lang` on the name tells a screen reader which language to use ([MDN `lang`](https://developer.mozilla.org/en-US/docs/Web/HTML/Global_attributes/lang)).

**Decision.** Applied on en, ja and ko for the header name 鄭宏璋 and for company names (experience, work, and the “now” line). The language is `zh-Hant-TW`, the same value as `<html lang>` on the Chinese page. `.han-name` keeps Manrope and that page’s `--font-cjk`, turns `locl` off, and does not include `system-ui`, which would follow the new language. The experience plus button stays as it is.

### What was the site, and what was noise

The owner's treemap and the audits "unused JavaScript 1,229 KiB" and "unused CSS 302 KiB" cannot be this site. The whole JavaScript graph is 215.3 KB gzip and the stylesheet is 12.7 KB gzip. A clean run reports about 73 KB of unused JavaScript, almost all of it the React and Next chunks, and the unused-CSS audit passes. Minify-JavaScript also passes. Those large figures are extensions and the Vercel preview toolbar (`vercel.live`).

Accessibility 95 and Best Practices 92 did not reproduce. Clean Chrome is 100 and 100, with no console errors and no failed touch-target audit. Nothing in our markup was changed for those two scores.

`vercel.json` cannot turn the toolbar off. The current control is the project setting, or the preview env `VERCEL_PREVIEW_FEEDBACK_ENABLED=0` ([Managing the toolbar](https://vercel.com/docs/vercel-toolbar/managing-toolbar)). This environment cannot write that variable. It is safe for Luke to set it on the preview; it does not change the production site.

### Render-blocking CSS, about 150 ms here and 600 ms on the preview

The only render-blocking request in a clean trace is our stylesheet, about 14 KB on the wire, estimated savings 150–160 ms. The owner's 600 ms adds the toolbar and the extension stylesheets on a real Slow 4G. The critical chain is document, then that CSS, then Noto Sans TC 400 and Manrope. First Contentful Paint equals LCP, and the LCP node is the hero title (or, on `/`, the language label). `font-display: swap` lets that text paint before the font files finish.

`experimental.inlineCss` was turned on and measured. Next documents it for small Tailwind CSS on a slow first visit ([inlineCss](https://nextjs.org/docs/app/api-reference/config/next-config-js/inlineCss)). The render-blocking insight went quiet, and the font files were discovered from the document. LCP got worse: `/en` 909 ms to 1,094 ms, `/` 1,000 ms to 1,293 ms. The HTML grew from about 41 KB to about 81 KB, and on this throttling profile that extra download costs more than the CSS round trip it removes. `optimizeCss` is not a config option in Next.js 16.4.6. Inlining was reverted. The linked stylesheet stays.

### Legacy JavaScript, 14 KiB

This one is real, and it is the same 14 KiB with or without extensions. The signals are `Array.prototype.at`, `flat`, `flatMap`, `Object.fromEntries`, `Object.hasOwn`, and `String.prototype.trimStart` / `trimEnd`, all inside Next's `polyfill-module`, which is prepended to the framework chunk. The file on disk is 1.4 KB. Lighthouse's 14 KiB is its estimate for those signals, not 14 KiB of application code. Next's own target is Chrome 111, Edge 111, Firefox 111, and Safari 16.4 ([supported browsers](https://nextjs.org/docs/architecture/supported-browsers)), and every one of those signals exists there. A browserslist entry would not remove the module; Next imports it directly. The production bundle now aliases that module to an empty file. `URL.canParse` lived in the same file and is only called from the dev hot-reloader. The separate nomodule polyfill (fetch, URL, Object.assign) is still emitted and is not downloaded by current Chrome. First-load JavaScript went from 144.3 KB to 143.9 KB gzip. The legacy-javascript insight scores 1 after the change.

### Forced reflow

Clean traces of `/` and `/en` have an empty reflow table. `/en#experience` once reported 55 ms with source `[unattributed]`, which is the fragment scroll, not a line in this repo. Two reads were still per frame once motion starts, so they are fixed even though the lab window did not bill them:

- The skill marquee read `scrollWidth` after writing `transform`. The width is measured on resize and when fonts finish loading.
- The hero canvas called `getBoundingClientRect()` on every frame to compute scroll progress. The section's document position is measured when the canvas resizes.

### Non-composited animations

A clean `/en#experience` trace flagged two elements. The header bar transitions `border-color` and `box-shadow` when a deep link opens already scrolled. Those properties are not composited. The first scroll position is now applied with the transition held off, and the 500 ms fade still runs when the visitor actually scrolls. The finished bar is unchanged: transparent at the top, glass border and shadow after 24 px.

The other element is `path.hero-underline`, animation `hero-draw`, property `stroke-dashoffset`. That draw is the approved line under the title. Replacing it with opacity would change the motion, so it stays. After the header change, it is the only non-composited animation in the clean trace. The owner's count of three includes this line, the header, and something that did not appear without the toolbar.
